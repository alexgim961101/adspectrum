## 001. 노드 파드 수용량 부족 — VPC CNI prefix delegation

- 날짜: 2026-08-22
- 상태: 결정 (SPEC 6장·9장 반영)

### 상황

VPC CNI 기본 모드에서 노드가 띄울 수 있는 파드 수는 인스턴스 타입이 정한다.
공식은 `ENI 수 × (ENI당 IP - 1) + 2`이고, t3.medium은 ENI 3개 / ENI당 IP 6개라 **17개**가 상한이다.
노드 2대면 클러스터 전체가 34개다.

계획된 상주 컴포넌트를 세면 kube-system 6, ArgoCD 7, kube-prometheus-stack 7,
KEDA·Argo Rollouts·ALB Controller 6, 애플리케이션 3 — 약 **29개**다.
여유가 5개뿐인데 KEDA는 consumer를 최대 10개까지 늘리도록 계획되어 있었다.

즉 부하를 주면 consumer 파드 절반이 `Pending`으로 남는다. 이 프로젝트는 클러스터 오토스케일러와
Karpenter를 범위에서 제외했으므로 **노드가 스스로 늘지도 않는다**. 노드그룹의 `max 4`는
아무도 조정하지 않으면 의미가 없다. 완료 조건 3번(consumer 0→N→0 스케일 그래프)이 성립하지 않는다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | VPC CNI prefix delegation 활성화 | ENI에 개별 IP 대신 `/28` 접두사를 할당해 t3.medium도 파드 110개까지 수용. 애드온 설정 변경뿐 |
| B | 노드를 t3.large로 교체 | 메모리가 4GB→8GB로 늘지만 IP 상한(35개)은 여전히 낮고 비용이 오른다 |
| C | KEDA 상한을 낮춘다 | 코드 변경은 가장 작지만 데모 곡선의 설득력이 줄어든다 |
| D | 클러스터 오토스케일러 도입 | 근본 해결이지만 SPEC 12장에서 범위 제외한 항목이고 1주 일정에 맞지 않는다 |

### 결정

**A + C를 함께 적용한다.** vpc-cni 애드온에 prefix delegation을 켜고, KEDA `maxReplicaCount`는 5로 둔다.

### 근거

A를 택한 이유는 인스턴스 타입을 바꾸지 않고 IP 병목만 제거할 수 있기 때문이다.
프라이빗 서브넷을 `/20`(4,091개)으로 넓게 잡아 둔 설계가 여기서 쓰인다 — prefix delegation은
서브넷에서 `/28` 블록 단위로 주소를 떼어가므로 좁은 서브넷에서는 오히려 할당 실패가 난다.

C를 함께 적용한 이유는 A만으로는 병목이 IP에서 **메모리**로 옮겨갈 뿐이기 때문이다.
t3.medium 2대의 실제 할당 가능 메모리는 8GB에 못 미치고, Prometheus와 ArgoCD가 그중 상당량을 쓴다.
consumer는 SQS를 폴링해 DynamoDB에 집계를 반영하는 가벼운 워커라 5개로도
큐 길이에 반응하는 0→N→0 곡선은 충분히 관측된다. 상한을 10으로 두고 파드가 `Pending`에 걸리는 것보다,
5로 두고 전부 정상 기동하는 편이 데모로서 정확하다.

B는 메모리 부족이 실제로 관측된 뒤에 쓴다. 지금 인스턴스를 키우면 원인 확인 없이 비용부터 늘리는 셈이다.

### 검증 결과 (2026-08-23)

첫 `apply` 후 두 노드 모두 `allocatable.pods = 110`으로 확인됐다. `aws-node`에 `ENABLE_PREFIX_DELEGATION=true`,
`WARM_PREFIX_TARGET=1`이 적용된 것도 확인했다. 애드온을 노드그룹보다 먼저 적용한 순서가 의도대로 동작했다.

### 남는 위험

IP 제약은 사라졌지만 한계가 메모리로 옮겨갔다. 측정된 할당 가능 메모리는 노드당 약 3.2GiB,
2대 합계 약 6.4GiB다. 여기에 ArgoCD, kube-prometheus-stack, KEDA, Argo Rollouts, ALB Controller가
올라가면 여유가 크지 않다. 2일차에 플랫폼 컴포넌트를 올린 직후 파드가 `Pending`에 걸리는지 확인하고,
메모리 부족이 원인이면 그때 B(t3.large)로 전환한다. 지금 미리 인스턴스를 키우지는 않는다.

## 002. EKS 엔드포인트 공개와 컨트롤플레인 로그 비활성화

- 날짜: 2026-08-22
- 상태: 결정

### 상황

EKS 모듈의 기본값 두 가지가 이 프로젝트의 제약과 맞지 않았다.
퍼블릭 엔드포인트는 기본이 **비활성**이라 그대로 두면 로컬에서 `kubectl`과 `helm`을 쓸 수 없고,
컨트롤플레인 로그는 기본이 **활성**(`audit`, `api`, `authenticator`)이라 CloudWatch 수집량만큼 과금된다.

### 결정

퍼블릭 엔드포인트는 열고 소스 IP 제한은 걸지 않는다. 프라이빗 엔드포인트도 함께 켠다.
컨트롤플레인 로그는 전부 끄고 로그 그룹도 만들지 않는다.

### 근거

엔드포인트를 연 이유는 부트스트랩 경로가 로컬 노트북 하나뿐이기 때문이다. 프라이빗 전용으로 두면
배스천이나 VPN이 필요한데, 그 자체가 이 프로젝트에서 증명하려는 대상이 아니면서 비용과 일정을 잡아먹는다.
API 엔드포인트는 IAM으로 인증되므로 열려 있다는 것이 곧 접근 가능하다는 뜻은 아니다.
소스 IP를 제한하지 않은 것은 작업 위치가 바뀔 때마다 `apply`를 다시 해야 하는 마찰 때문이고,
실서비스라면 제한하거나 프라이빗 전용 + 배스천으로 가는 것이 맞다.
프라이빗 엔드포인트를 함께 켠 이유는 노드가 VPC 내부 경로로 컨트롤플레인에 붙어 NAT 트래픽을 줄이기 때문이다.

로그를 끈 이유는 audit 로그의 양이 많고 ArgoCD처럼 API 서버를 지속적으로 폴링하는 컴포넌트가
있으면 더 늘기 때문이다. 이 프로젝트의 관측 책임은 Prometheus와 Grafana에 있고 완료 조건 어디에도
컨트롤플레인 로그가 들어가지 않는다. 보안 감사가 요구되는 환경이라면 최소한 `audit`은 켜야 한다.

### 남는 위험

컨트롤플레인 로그가 없으므로 API 서버 수준의 문제(권한 거부 원인, 웹훅 실패 등)를 사후에 추적할 수 없다.
그런 문제를 만나면 일시적으로 `audit`만 켜서 재현하고 다시 끈다.

## 003. GitHub Actions OIDC 프로바이더를 만들지 않고 참조한다

- 날짜: 2026-08-22
- 상태: 결정

### 상황

CI가 장기 액세스 키 없이 ECR에 푸시하려면 계정에 GitHub Actions OIDC 프로바이더가 있어야 한다.
그런데 이 프로바이더는 **계정당 하나만 존재할 수 있는 공용 리소스**이고, 대상 계정에는 이미
다른 프로젝트가 만들어 둔 것이 있었다. Terraform이 새로 만들려 하면 apply가 중복으로 실패한다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 데이터 소스로 기존 것을 참조 | 소유하지 않으므로 destroy가 다른 프로젝트에 영향을 주지 않는다 |
| B | `terraform import`로 소유권을 가져온다 | destroy할 때 계정의 다른 CI가 전부 끊긴다 |
| C | 조건부 생성 플래그를 둔다 | 계정 상태에 따라 동작이 갈리는 설정이 하나 늘어난다 |

### 결정

**A.** `aws_iam_openid_connect_provider` 데이터 소스로 참조만 한다.

### 근거

이 프로젝트는 비용 때문에 매일 `terraform destroy`를 실행한다. B를 택하면 그때마다 같은 계정의
다른 프로젝트 CI 인증이 함께 끊긴다. 리소스의 수명이 프로젝트보다 길고 소유자가 따로 있다면
IaC에서도 만들지 않고 참조하는 것이 맞다.

대가는 이 코드가 자기완결적이지 않다는 점이다. 프로바이더가 없는 새 계정에서는 `apply`가 실패하므로,
사전 조건임을 RUNBOOK에 적고 필요한 생성 명령을 함께 남긴다.

### 검증 결과 (2026-08-23)

첫 `destroy` 후 GitHub Actions OIDC 공급자가 계정에 그대로 남은 것을 확인했다.
반면 이 프로젝트가 소유한 EKS 클러스터용 OIDC 공급자는 함께 삭제됐다.
소유와 참조를 나눈 판단이 의도대로 동작했고, B(import)를 택했다면 이 시점에 계정의
다른 프로젝트 CI 인증이 끊겼을 것이다.

## 004. 스펙에 없던 ALB Controller IRSA 역할 추가

- 날짜: 2026-08-23
- 상태: 결정 (SPEC 6장 보완)

### 상황

2일차 컴포넌트를 구성하다 스펙 6장의 IRSA 매핑 표에 **AWS Load Balancer Controller가
빠져 있는 것**을 발견했다. 이 컨트롤러는 Ingress를 보고 실제 ALB와 리스너, 대상 그룹,
보안 그룹 규칙을 만들기 때문에 상당한 AWS 권한이 필요하다. 권한이 없으면 Ingress가
생성되지 않고, 2일차 완료 기준인 "전 앱 Synced/Healthy"를 채울 수 없다.
3일차 API 노출과 6일차 카나리 트래픽 분할도 전부 여기에 걸린다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 벤더가 발행한 공식 정책을 그대로 가져와 쓴다 | 검증된 권한 집합. 다만 쓰지 않는 권한도 포함된다 |
| B | 실제로 필요한 동작만 추려 직접 작성한다 | 최소 권한에 가깝지만 누락 시 Ingress가 조용히 실패한다 |
| C | 커뮤니티 IAM 모듈의 내장 정책을 쓴다 | 코드는 짧지만 이 프로젝트에 IAM 관리 방식이 두 가지가 된다 |

### 결정

**A.** 공식 정책 JSON을 `infra/modules/iam/policies/`에 버전과 출처를 명시해 보관하고
`file()`로 읽어 인라인 정책으로 붙인다.

### 근거

이 프로젝트의 다른 IRSA 정책은 전부 파드가 실제로 호출하는 API만 나열한 최소 권한이다.
Load Balancer Controller만 예외로 둔 이유는 필요한 동작이 80개가 넘고 컨트롤러 버전마다
바뀌기 때문이다. B를 택하면 누락된 권한 하나 때문에 Ingress 생성이 실패하는데, 원인이
컨트롤러 로그에만 남아 찾는 데 시간이 든다. 7일 일정에서 감수할 위험이 아니다.

대신 무엇을 주는지 모르고 쓰지는 않는다. `policies/README.md`에 서비스별 동작 수와
이 프로젝트에서 쓰지 않는 권한(WAF, Shield, ACM, Cognito)을 정리했다.
"최소 권한"과 "벤더 정책 신뢰"의 경계를 어디에 두었는지가 기록으로 남아야 한다.

C를 택하지 않은 이유는 IAM 역할 5개는 직접 작성하고 하나만 모듈로 만드는 구성이
읽는 사람에게 일관성 없게 보이기 때문이다.

### 남는 위험

정책에 이 프로젝트가 쓰지 않는 WAF·Shield·ACM·Cognito 권한이 포함된다. 잘라낼 수는 있지만
다음 컨트롤러 버전에서 조용히 깨질 수 있어 그대로 둔다. 실제 운영이라면 컨트롤러 버전을
올릴 때 정책 diff를 확인하는 절차를 두어야 한다.

## 005. 매니페스트에 AWS 계정 ID를 그대로 적는다

- 날짜: 2026-08-23
- 상태: 결정

### 상황

IRSA는 ServiceAccount 어노테이션에 역할 ARN 전체를 요구하고, ARN에는 계정 ID가 들어간다.
이 저장소는 공개를 전제로 하므로 계정 ID가 노출될 수 있다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 매니페스트에 ARN을 그대로 적는다 | Git에 있는 것이 곧 클러스터 상태라는 GitOps 전제가 유지된다 |
| B | 부트스트랩 시점에 치환한다 | 계정 ID는 감춰지지만 Git만으로는 배포가 재현되지 않는다 |
| C | 저장소를 비공개로 둔다 | 공개해서 보여 준다는 목적과 충돌한다 |

### 결정

**A.** ARN을 매니페스트에 그대로 적는다.

### 근거

B는 GitOps의 핵심 전제를 깬다. Git을 봐도 실제로 무엇이 배포되는지 알 수 없게 되고,
"Git이 유일한 진실"이라는 주장이 성립하지 않는다. 이 프로젝트가 증명하려는 것이 바로
그 전제이므로, 그것을 훼손하면서 얻는 이득이 없다.

계정 ID는 자격증명이 아니다. AWS도 비밀로 분류하지 않으며, 이것만으로는 어떤 접근도
불가능하다. 실제 방어선은 IAM 정책과 신뢰 정책 조건이고, 그쪽은 네임스페이스와
ServiceAccount 이름까지 좁혀 두었다.

### 남는 위험

계정 ID가 알려지면 역할 이름 추측을 통한 열거 시도의 출발점이 될 수 있다. 다만 신뢰 정책이
이 클러스터의 특정 ServiceAccount로 제한되어 있어 외부에서 역할을 맡을 수 없다.
민감도가 높은 조직이라면 저장소를 비공개로 두거나 배포 계정을 분리하는 것이 맞다.

## 006. ALB Controller가 IMDS에 접근하지 못해 기동 실패

- 날짜: 2026-08-23
- 상태: 해결

### 증상

2일차 부트스트랩 후 `aws-load-balancer-controller` 파드가 `CrashLoopBackOff`에 빠졌다.
IRSA 어노테이션은 정상이었고 역할도 붙어 있었는데 로그는 이렇게 나왔다.

```
unable to initialize AWS cloud
error: failed to get VPC ID: failed to fetch VPC ID from instance metadata:
       get mac metadata: operation error ec2imds: GetMetadata, canceled, context deadline exceeded
```

권한 문제가 아니라 **컨트롤러가 자기가 속한 VPC를 찾지 못하는** 문제였다.

### 원인

컨트롤러는 VPC ID와 리전을 EC2 인스턴스 메타데이터(IMDS)에서 읽는다. 그런데 노드 시작
템플릿의 `HttpPutResponseHopLimit`이 **1**이었다. 파드는 CNI를 거쳐 한 홉 떨어져 있으므로
홉 제한이 1이면 IMDS에 도달할 수 없다. 이건 결함이 아니라 보안 기본값이다 — 파드가 IMDS에
닿으면 **노드의 IAM 역할 자격증명을 훔칠 수 있어** IRSA로 권한을 나눈 의미가 사라진다.

### 연쇄 피해

컨트롤러가 죽어 있는 동안 그것이 등록한 mutating webhook(`mservice.elbv2.k8s.aws`)은 살아 있었다.
웹훅에 엔드포인트가 없으니 **클러스터 전체에서 Service 생성이 실패**했고, KEDA와
kube-prometheus-stack의 동기화가 함께 무너졌다. 표면적으로는 세 앱이 각각 고장 난 것처럼 보였지만
원인은 하나였다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | `vpcTags`로 VPC를 태그 조회하게 한다 | IMDS 불필요. VPC ID가 바뀌어도 매니페스트가 그대로다 |
| B | 노드의 IMDS 홉 제한을 2로 올린다 | 동작하지만 모든 파드가 노드 자격증명에 접근할 수 있게 된다 |
| C | `vpcId`를 매니페스트에 직접 적는다 | destroy/apply마다 VPC ID가 바뀌어 매일 고쳐야 한다 |

### 결정

**A.** `region`을 명시하고 VPC는 `vpcTags`(`Project=adspectrum`, `Environment=dev`)로 찾게 했다.

### 근거

B는 이 프로젝트가 IRSA로 파드별 권한을 나눈 것과 정면으로 충돌한다. 홉 제한 1은 그 설계를
강제하는 장치이므로, 컨트롤러 하나를 위해 클러스터 전체의 방어선을 낮출 이유가 없다.

C는 매일 인프라를 내렸다 올리는 이 프로젝트의 운영 방식과 맞지 않는다. Git에 적힌 값이 하루 만에
낡는다면 "Git이 유일한 진실"이라는 전제가 성립하지 않는다.

A는 태그가 provider `default_tags`로 항상 붙기 때문에 VPC를 몇 번을 다시 만들어도 유효하다.
필요한 `ec2:DescribeVpcs` 권한은 벤더 정책에 이미 포함되어 있었다.

### 함께 고친 것

동기화가 한 번 실패한 뒤 `OutOfSync`에서 멈춰 사람이 개입해야 했다. 자식 Application에
재시도 정책(`limit 5`, 15초부터 지수 백오프)을 추가해 일시적 실패에서 스스로 회복하게 했다.
웹훅이나 CRD 준비 순서 때문에 첫 시도가 실패하는 것은 흔한 일이라, 재시도가 없으면
클러스터를 다시 만들 때마다 같은 개입이 필요하다.

### 배운 것

어드미션 웹훅을 등록하는 컨트롤러가 죽으면 그 여파가 컨트롤러 자신에 그치지 않는다.
증상이 여러 곳에서 동시에 나타날 때 각각을 따로 고치려 들면 시간을 잃는다.
이번에는 세 앱이 고장 난 것처럼 보였지만 실제 원인은 하나였고, 그것을 고치자 나머지는 저절로 풀렸다.

## 007. 앱 3종을 독립 패키지로 유지한다

- 날짜: 2026-08-25
- 상태: 확정

### 상황

3일차에 앱 3종을 구현하면서 겹치는 코드가 생겼다. JSON 로깅 설정(약 40줄), 환경변수

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 앱마다 독립 패키지. 겹치는 코드는 복사 | 빌드 컨텍스트가 `apps/<앱>/` 하나. 배포 단위가 서로 독립 |

그때 B로 옮기는 편이 낫다.

이벤트 스키마가 generator와 consumer에 각각 있는 것은 중복이 아니라 **경계**다. 둘 사이의
계약은 파이썬 타입이 아니라 SQS에 실린 JSON이고, 그 계약은 `docs/API.md`에 적는다.
한쪽을 고치면 다른 쪽이 자동으로 따라오는 구조였다면, 실제로는 호환성 없는 변경을
배포한 뒤에야 알아차렸을 것이다.

## 009. 스키마 위반 메시지 하나가 컨슈머를 영구히 멈출 뻔했다

- 날짜: 2026-08-25
- 상태: 해결

### 증상

`aggregate()`의 테스트를 쓰는 중, 오프셋 없는 `occurred_at`("2026-08-25T09:30:12")을
넣은 케이스에서 예외가 함수 밖으로 튀어나왔다.

### 원인

깨진 메시지를 걸러 내는 `try` 블록이 `parse_event()`만 감싸고 있었고, 분 버킷을 계산하는
`minute_bucket()`은 블록 밖에 있었다. `minute_bucket()`이 던지는 `ValueError`는 잡히지 않는다.

문제는 여기서 끝나지 않는다. 이 설계에서 **처리 실패한 메시지는 삭제하지 않는다**.
따라서 예외로 폴링이 죽으면 그 메시지는 큐에 남고, 재시작한 컨슈머가 같은 메시지를 다시 받아
같은 자리에서 또 죽는다. 메시지 하나가 파이프라인 전체를 무한히 멈추는 poison pill이 된다.

### 결정

버킷 키 계산을 `try` 블록 안으로 옮겼다. 위반 메시지는 집계에서 빠지고 `ReceiptHandle`도
삭제 목록에 들어가지 않으므로, SQS가 3회 재전달한 뒤 DLQ로 옮긴다.

### 배운 것

"실패한 메시지를 삭제하지 않는다"는 안전한 규칙이지만, 그 앞단에서 **어떤 실패를 걸러 낼지**
범위를 잘못 잡으면 같은 규칙이 정확히 반대로 작동한다. 재전달이 복구 수단이 되려면
재전달된 메시지가 다음 번에는 다르게 처리되어야 하는데, 여기서는 그렇지 않았다.

DLQ를 만들어 둔 것이 이 설계의 전제였고, 그 전제가 코드에서 성립하는지는 테스트가 확인했다.

## 010. GitHub OIDC가 immutable subject로 바뀌어 CI 인증이 실패

- 날짜: 2026-08-25
- 상태: 해결

### 증상

4일차 CI의 첫 실행에서 변경 감지와 테스트는 통과했는데 ECR 푸시 단계가 죽었다.

```
Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity
```

역할의 신뢰 정책, OIDC 공급자의 대상(audience), 워크플로의 `id-token: write` 권한을
차례로 확인했지만 전부 정상이었다. 공급자도 `sts.amazonaws.com`을 허용하고 있었다.

### 원인

추측을 멈추고 토큰의 실제 클레임을 찍었다. 일회성 워크플로에서 OIDC 토큰을 발급받아
페이로드만 디코드했다(토큰 자체는 출력하지 않는다).

```json
{
  "sub": "repo:alexgim961101@74600075/adspectrum@1343590586:ref:refs/heads/main",
  "aud": "sts.amazonaws.com",
  "repository": "alexgim961101/adspectrum"
}
```

GitHub이 **immutable subject claim**으로 전환해 `sub`에 소유자와 저장소의 숫자 ID를
함께 싣고 있었다. 1일차에 작성한 신뢰 정책은 이름만 담은 예전 형식
`repo:alexgim961101/adspectrum:ref:refs/heads/main`을 `StringEquals`로 고정하고 있어
문자열이 달라 매칭에 실패한 것이다.

`gh api repos/<owner>/<repo>/actions/oidc/customization/sub`가 `use_immutable_subject: false`를
반환하는데도 실제 토큰은 ID가 박힌 형식이었다. 설정 값만 믿었다면 원인을 못 찾았을 것이다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 신뢰 정책을 ID가 박힌 새 형식으로 교체 | 토큰과 일치. ID는 불변이라 이름 변경에도 안전 |
| B | 두 형식을 모두 허용 (`StringEquals`에 값 두 개) | 롤백 대비는 되지만 예전 형식의 취약점이 남는다 |
| C | `sub`를 `StringLike`로 느슨하게 | 조건이 넓어져 고정 효과가 줄어든다 |

### 결정

**A.** `repo:<owner>@<owner_id>/<repo>@<repo_id>:ref:refs/heads/<branch>` 형식으로 바꿨다.
숫자 ID는 `locals.tf`에 두고, 확인 명령을 주석으로 남겼다.

### 근거

B는 예전 형식을 남겨 두는 것이고, 그 형식이 폐기되는 이유 자체가 보안 문제다. 저장소 이름은
바꿀 수 있고 반납한 이름은 다른 사람이 가져갈 수 있다. 이름으로만 신뢰를 고정하면 그 경로로
남의 저장소 워크플로가 우리 역할을 맡을 수 있다. GitHub이 ID를 넣기 시작한 게 정확히 그 구멍을
막으려는 것이므로, 굳이 열어 둘 이유가 없다.

숫자 ID가 매니페스트에 드러나는 가독성 손해는 있지만, 계정 ID를 그대로 적기로 한 결정
(DECISIONS 005)과 같은 성격이다 — Git에 적힌 값이 곧 배포되는 값이어야 한다.

### 배운 것

인증 실패를 디버깅할 때 **설정을 세 번 읽는 것보다 토큰을 한 번 열어 보는 것이 빠르다.**
이번에는 양쪽 설정이 모두 "맞게" 보였고, 틀린 것은 그 사이에 오가는 값이었다.
GitHub API가 보고하는 설정과 실제 발급 토큰이 달랐다는 점도 같은 교훈이다.

## 011. CI 워크플로를 한 파일로 두고 이미지 재빌드 범위를 좁힌다

- 날짜: 2026-08-25
- 상태: 확정

### 상황

스펙 8장은 `ci.yaml`(push)과 PR 워크플로를 따로 두고, 트리거 경로를
`apps/**`, `charts/**`로 잡았다. 구현하면서 두 가지를 조정했다.

### 결정 1 — 파일을 나누지 않는다

`push`와 `pull_request`를 한 파일에서 처리하고, AWS를 건드리는 잡에만
`if: github.event_name == 'push'`를 건다.

변경 감지 로직이 양쪽에 똑같이 필요한데, 파일을 나누면 그 로직이 두 벌이 되고
한쪽만 고치는 사고가 난다. 권한 분리는 파일이 아니라 잡 단위 `permissions`와
IAM 신뢰 정책이 담당한다 — 역할이 `refs/heads/main`으로 잠겨 있어 PR에서는
워크플로가 무슨 짓을 해도 역할을 맡을 수 없다. 실제로 PR 실행에서 이미지 푸시와
태그 갱신 잡이 `skipped`로 남는 것을 확인했다.

### 결정 2 — 차트만 바뀌면 이미지를 다시 굽지 않는다

트리거는 스펙대로 `apps/**`, `charts/**` 둘 다 받되, **빌드 매트릭스는
`apps/<앱>/`이 바뀐 앱만** 담는다. 차트 변경은 ArgoCD가 Git에서 직접 받아 가므로
새 이미지가 필요 없다. 대신 차트가 바뀌면 `helm lint`와 실제 values를 얹은
`helm template`을 돌려 렌더링 오류를 머지 전에 잡는다.

빌드는 앱당 1~2분이 걸린다. 주석 한 줄 고친 차트 변경으로 세 앱을 다시 굽는 것은
시간도 시간이지만, ECR에 내용이 같은 이미지가 태그만 다르게 쌓인다.

### 루프 방지를 세 겹으로 둔 이유

CI가 마지막에 `deploy/values`를 갱신하고 main에 되민다. 그 커밋이 다시 CI를 부르면
무한 루프가 된다. 방어선이 셋이다.

1. 트리거 `paths`에 `deploy/**`가 없다 — 되민 커밋은 애초에 조건에 안 걸린다
2. 커밋 메시지의 `[skip ci]`
3. `GITHUB_TOKEN`으로 만든 푸시는 워크플로를 다시 부르지 않는다는 GitHub 규칙

하나로 충분해 보이지만 셋 다 성격이 다르다. 1은 경로를 넓히는 순간 깨지고,
2는 커밋 메시지에 의존하며, 3은 토큰을 PAT로 바꾸는 순간 사라진다. 나중에 누군가
하나를 건드려도 나머지가 남는다.

실제로 이 프로젝트에서 2번이 예상 밖으로 작동한 적이 있다. **워크플로를 추가하는
커밋의 본문에 `[skip ci]`를 설명으로 적었더니 GitHub이 그대로 인식해 실행을 건너뛰었다.**
커밋 메시지 전체가 검사 대상이라는 것을 몸으로 확인한 셈이다.

## 012. buildx의 attestation이 불변 태그를 차지해 이미지가 깨졌다

- 날짜: 2026-08-28
- 상태: 확정

### 증상

클러스터를 새로 만든 뒤 ECR이 비어 있어 앱 3종을 손으로 다시 구웠다. `docker push`가
세 번 모두 400을 냈는데, `aws ecr describe-images`에는 태그가 멀쩡히 보였다.

```
failed commit on ref "manifest-sha256:...": unexpected status from PUT request
to .../adspectrum/metrics-api/manifests/5d2bc96: 400 Bad Request
```

태그가 가리키는 매니페스트를 열어 보니 레이어가 하나뿐이고 1.6KB였다. 로컬 이미지는
8레이어 72MB였다.

```json
"mediaType": "application/vnd.in-toto+json",
"annotations": { "in-toto.io/predicate-type": "https://slsa.dev/provenance/v0.2" }
```

### 원인

buildx는 기본으로 provenance attestation을 함께 만든다. `--load`로 로컬에 넣은 뒤
`docker push`로 밀면 두 매니페스트가 같은 태그를 두고 차례로 올라간다. ECR 리포지토리를
태그 불변(IMMUTABLE)으로 만들어 두었으므로, 태그를 먼저 차지한 쪽이 이기고 나머지는
400으로 거부된다. 결과가 attestation 쪽이 남은 것으로 보아 그쪽이 먼저 올라갔다고
판단했다 — 푸시 순서 자체를 로그로 확인하지는 않았다.

`describe-images`가 태그를 보여 주기 때문에 푸시가 끝난 것처럼 보인다는 점이 나쁘다.
그대로 배포했다면 파드가 뜨지 않는 이유를 런타임에 가서야 알았을 것이다.

### 선택지

1. 이미지를 지우고 같은 태그로 다시 올린다 — 불변 태그를 되찾으려면 삭제가 필요하다
2. attestation을 끄고 새 태그(현재 HEAD)로 올린다
3. 리포지토리를 태그 가변으로 바꾼다

### 결정

2번. `--provenance=false`로 다시 굽고 태그를 `6725cb1`로 올린 뒤 `deploy/values`를
갱신했다.

### 근거

태그 불변은 "태그가 곧 산출물의 신원"이라는 규칙이고, 이번 사고는 오히려 그 규칙이
깨진 이미지를 조용히 덮어쓰지 못하게 막아 준 사례다. 규칙을 끄는 3번은 증상을 숨긴다.
1번의 삭제는 되돌릴 수 없고, 어차피 커밋마다 새 태그를 만드는 것이 정상 경로다.
남은 attestation 태그 3개는 무해하며 destroy 때 리포지토리와 함께 사라진다.

### 배운 것

RUNBOOK에 적혀 있던 절차는 `buildx build --push`, 즉 빌드와 푸시가 한 명령이었다.
그것을 "미리 빌드해 두고 나중에 푸시"로 쪼개 시간을 아끼려던 순간 문서에 없는 경로로
들어갔고, 거기서 깨졌다. 검증된 절차를 임의로 최적화하면 검증 범위 밖으로 나간다.

`--provenance=false` 없이 `buildx build --push`만으로도 되는지는 이번에 확인하지
않았다. 이전 배포가 그 명령으로 성공했으니 문제없을 가능성이 높지만, 확인 전까지는
RUNBOOK에 두 옵션을 함께 적어 둔다. `[미검증]`

## 013. 분석이 "데이터 없음"을 "정상"으로 읽어 결함이 관문을 통과했다

- 날짜: 2026-08-28
- 상태: 확정

### 증상

`FAULT_RATE=0.5`(응답 절반이 500)인 버전을 배포했는데, 20% 단계 분석이 **통과**했고
50%까지 올라간 뒤에야 롤백됐다. 결함 버전이 전체 트래픽의 절반을 20초쯤 받았다.

측정값을 열어 보니 앞의 두 번이 0이었다.

```
14:14:12  Successful  value=[0]
14:14:32  Successful  value=[0]
14:14:52  Failed      value=[0.41988]   ← 세 번째에야 진짜 값
```

`failureLimit: 1`이라 실패 한 번은 허용된다. 그래서 이 분석은 "성공"으로 끝났다.

### 원인

분석 쿼리를 `or vector(0)` / `or vector(1)`로 감싸 둔 것이 원인이다. 카나리 파드가 막
떠서 아직 스크레이프되지 않은 동안에는 분자·분모가 모두 빈 벡터인데, 가드가 그것을
`0 / 1 = 0`으로 만든다. **지표가 없다는 사실이 에러율 0%로 계산된 것이다.**

가드 자체는 필요했다. 없으면 같은 구간에서 `result[0]`이 존재하지 않아 분석이 오류로
끝나고, 결함이 아니라 타이밍 때문에 배포가 막힌다. 문제는 가드가 아니라 **물어보는
시점**이었다. 파드가 뜨자마자 물어보면 어떤 답이 나오든 근거가 없다.

### 선택지

1. `initialDelay`로 첫 측정을 미룬다
2. 가드를 없애고 데이터 없음을 오류로 처리한다 (fail closed)
3. 쿼리에 최소 요청 수 조건을 넣어 표본이 적으면 판단하지 않는다

### 결정

1번. `initialDelay: 45s`. 스크레이프 간격이 15초이므로 `rate(...[1m])`에 점이 두 개
이상 쌓일 시간을 준다.

### 근거

2번은 트래픽이 정말 없는 배포까지 롤백시킨다. 이 프로젝트에서 카나리 트래픽은 k6가
공급하는 것이라 "요청이 없다"는 상황이 정상적으로 발생한다. 3번은 정확하지만 쿼리가
길어지고, 최소 표본 수라는 상수를 또 하나 정해야 한다. 1번은 원인(시점)을 그대로
겨냥하면서 값 하나로 끝난다.

### 검증 결과 (2026-08-28)

같은 결함을 다시 주입해 재현했다. 첫 측정부터 실제 값이 나왔고 20% 단계에서 중단됐다.

```
14:24:10  Failed  value=[0.5052]
14:24:30  Failed  value=[0.4832]    → RolloutAborted (Step 1/4, weight 20)
```

임계값이 실제로 5% 기준선인지도 확인했다. `FAULT_RATE=0.02`(2%) 버전은 분석을 통과해
20% → 50% → 100%로 승격됐다(측정값 0.011 ~ 0.027). 오류가 있으면 무조건 막는 것이
아니라 기준선으로 판단한다는 뜻이다.

### 배운 것

가드를 넣을 때는 "무엇을 무엇으로 바꾸는가"를 봐야 한다. 이 가드는 오류를 통과로
바꿨다. 안전장치에서 그 방향의 교환은 위험하다 — 실패는 시끄럽지만, 잘못된 통과는
조용하다. 처음 롤백이 성공했을 때 단계 번호를 보지 않았다면 이 결함을 그대로 두고
"자동 롤백 동작함"이라고 적었을 것이다.

## 014. 큐 깊이 패널을 CloudWatch가 아니라 KEDA 지표로 그린다

- 날짜: 2026-08-28
- 상태: 확정

### 상황

SPEC 9장은 대시보드의 큐 깊이 패널을 CloudWatch 데이터소스로 그리기로 했다. 구현
시점에 두 가지가 걸렸다. SQS의 CloudWatch 지표는 해상도가 분 단위 이상이라 10분짜리
스케일링 데모에서 계단처럼 보이고, 무엇보다 **KEDA가 판단에 쓴 값과 다른 값**이다.

### 결정

KEDA 오퍼레이터의 Prometheus 지표(`keda_scaler_metrics_value`)로 그린다. KEDA 차트의
`prometheus.operator.enabled`와 `podMonitor.enabled`를 켰다. CloudWatch 데이터소스는
DLQ 패널이 계속 쓴다.

### 근거

대시보드의 목적은 "왜 이때 레플리카가 늘었나"를 설명하는 것이다. 스케일러가 실제로
읽은 값을 그리면 그래프와 동작이 어긋날 수 없다. CloudWatch 값을 그리면 둘이 미세하게
다를 때 "그래프는 200인데 왜 안 늘지" 같은 질문이 생기고, 그 차이는 데모로 설명할 수
없는 종류다.

CloudWatch를 완전히 버리지 않은 이유는 DLQ 깊이가 Prometheus에는 없기 때문이다.
Grafana의 IRSA 경로도 그 패널로 계속 증명된다.

### 검증 결과 (2026-08-28)

`keda_scaler_metrics_value{scaledObject="event-consumer"}`가 수집되는 것을 확인했고,
부하 시나리오에서 큐 깊이와 레플리카 수가 한 화면에서 함께 움직이는 것을 확인했다.
Grafana 데이터소스 health는 Prometheus `OK`, CloudWatch는 metrics API 성공이다.
CloudWatch **logs** API는 400을 반환하는데, Grafana IRSA에 로그 권한을 주지 않았기
때문이고 이 프로젝트는 로그 조회를 쓰지 않는다.

## 015. IaC에도 CI를 붙이고, 그러기 위해 상태를 S3로 옮긴다

- 날짜: 2026-08-29
- 상태: 확정

### 상황

`apps/`와 `charts/`는 CI가 지키는데 `infra/`는 아무도 보지 않았다. 트리거 경로에
`infra/**`가 없어서 Terraform 코드는 검사 없이 머지됐다. IaC로 인프라를 관리한다고
말하면서 정작 IaC만 검증 밖에 있었다.

`plan`을 PR에 붙이려면 CI가 상태에 접근해야 한다. 그런데 상태는 로컬 파일이었고
(DECISIONS에 "1인 단기 프로젝트라 S3 백엔드의 부트스트랩 비용을 생략한다"고 적어
두었다), 러너에는 그 파일이 없다.

### 선택지

1. 정적 검사(fmt·validate·tflint·trivy)만 넣고 `plan`은 포기한다 — 상태가 필요 없다
2. S3 백엔드로 옮기고 `plan`까지 넣는다 — 이전 결정을 뒤집는다
3. Terraform Cloud 같은 관리형 백엔드를 쓴다

### 결정

2번. 상태를 S3 + DynamoDB 잠금으로 옮기고, `infra/**` 변경에 대해 정적 검사와
`plan`을 돌린다. PR에는 plan 결과를 코멘트로 남긴다.

### 근거

이전 결정을 뒤집은 이유는 전제가 바뀌었기 때문이다. "부트스트랩 비용이 아깝다"는
판단은 상태를 사람만 읽을 때 성립한다. CI가 읽어야 하는 순간 로컬 파일은 선택지가
아니게 된다. 3번은 계정 하나로 끝나는 프로젝트에 외부 서비스 의존을 더한다.

**뒤집기 좋은 시점이기도 했다.** 마침 `destroy` 직후라 상태에 리소스가 0개였고,
이전에 실패할 것이 없었다. 리소스 74개를 담은 상태를 옮기는 것과는 위험이 다르다.

### 백엔드 리소스를 Terraform으로 만들지 않는다

버킷과 잠금 테이블은 CLI로 만들고 절차를 RUNBOOK 2장에 적었다. 자기 상태를 담은
저장소를 자기 상태로 관리하면 `destroy`가 자기 발밑을 지운다. 이것은 GitHub OIDC
공급자를 만들지 않고 참조만 하는 것과 같은 범주다(DECISIONS 003) — 환경보다 오래
사는 계정 수준 리소스다.

### CI 역할도 환경 밖에 둔다

`plan`용 역할을 `infra/envs/dev`에 넣으면 `destroy`와 함께 사라진다. 환경이 내려가
있을 때야말로 plan이 "무엇이 생길지"를 보여줘야 하는데, 그 순간 역할이 없어서 plan을
돌릴 수 없다. 순환이다. 그래서 `adspectrum-ci-plan`도 계정 사전 조건으로 만들었다.

기존 ECR 푸시 역할(`adspectrum-github-actions`)은 여전히 환경 안에 있다. 환경이
내려가 있으면 CI의 이미지 푸시도 실패한다는 뜻이고, 같은 이유로 밖으로 빼는 것이
맞다. 이번 범위에서는 건드리지 않았다.

### 읽기 전용 역할에 ReadOnlyAccess를 붙인 트레이드오프

`plan`은 설정에 등장하는 모든 서비스를 조회한다. 필요한 액션을 손으로 열거하면
하나만 빠져도 plan이 실패하고, 실패한 plan은 아무도 읽지 않게 된다. 그래서 관리형
`ReadOnlyAccess`를 붙이되, 명시적 Deny로 실질적인 위험을 잘라 냈다.

- 상태 버킷 외의 S3 객체는 읽지 못한다 (`NotResource`)
- 상태 버킷에 쓰지 못한다 — plan은 상태를 읽기만 한다
- Secrets Manager 값, SSM 파라미터, `kms:Decrypt`는 거부

신뢰 정책은 이 저장소의 `main` push와 PR 두 subject만 허용한다. 임의 브랜치는
제외했고, 포크 PR에는 OIDC 토큰이 발급되지 않으므로 워크플로에도 같은 조건을 걸어
실패한 잡이 쌓이지 않게 했다.

### 무시 목록에는 이유를 적는다

`trivy config`가 MEDIUM 2건, LOW 2건을 지적했다. DynamoDB PITR은 켰다(저장량이
MB 단위라 비용이 사실상 없다). 나머지 셋은 `.trivyignore.yaml`에 **왜 지금
받아들이는지와 언제 다시 볼지**를 적어 예외로 뒀다. 이유 없는 무시가 쌓이면 검사
자체가 장식이 된다.

외부 모듈(`terraform-aws-modules`)은 검사 대상에서 뺐다. 고칠 수 없는 지적을 계속
보면 무시하는 데 익숙해지고, 그 습관은 우리 코드의 지적에도 옮는다.

### 검증 결과 (2026-08-29)

이 워크플로를 담은 PR이 스스로의 첫 시험 대상이 됐다. 두 번 실패하고 고쳤다.

**1. `aquasecurity/trivy-action@0.28.0`은 존재하지 않는 태그였다.** 맞는 버전을 찾는
대신 바이너리를 직접 받는 방식으로 바꿨다. 서드파티 액션 의존이 하나 줄고, 로컬에서
검증할 때와 CI가 같은 버전을 쓰게 된다.

**2. `ssm:GetParameter` 전면 Deny가 공개 파라미터까지 막았다.**

```
AccessDeniedException: not authorized to perform: ssm:GetParameter on resource:
arn:aws:ssm:ap-northeast-2::parameter/aws/service/eks/optimized-ami/1.36/...
with an explicit deny in an identity-based policy
```

EKS 모듈이 노드 AMI 버전을 조회하는 경로였다. `/aws/service/...`는 AWS가 모두에게
제공하는 공개 파라미터라 **ARN에 계정 ID가 없다.** Deny 범위를
`arn:aws:ssm:*:<계정>:parameter/*`로 좁혀 우리 계정이 소유한 파라미터만 막았다.
의도했던 것(우리 비밀을 못 읽게 한다)은 그대로 지키면서 공개 조회는 통과한다.

배운 것: 최소 권한을 Deny로 구현하면 "무엇을 막는가"만큼 "무엇까지 막히는가"를
봐야 한다. 다행히 이런 Deny는 조용히 지나가지 않고 눈에 띄게 깨지지만, 그것도 plan이
그 리소스를 건드릴 때뿐이다.

**최종 결과**: 정적 검사 통과, plan이 `74 to add, 0 to change, 0 to destroy`를 내고
PR에 코멘트가 게시됐다. 상태 잠금 획득과 해제도 로그에서 확인했다.

## 016. 감지에서 통보까지 고리를 잇는다

- 날짜: 2026-08-29
- 상태: 확정 (전송 검증은 다음 클러스터 가동 때)

### 상황

지표는 모으고 대시보드도 있는데, **사람이 화면을 보고 있어야만 장애를 안다.**
`PrometheusRule`이 하나도 없었고 Alertmanager는 꺼져 있었다("완료 조건에 없다"는
이유로 파드와 메모리를 아꼈다). 관측은 있고 통보가 없는 상태였다.

### 결정

각 앱 차트에 `PrometheusRule`을 두고, Alertmanager를 켜서 Slack으로 보낸다.
규칙을 앱 차트에 두는 이유는 감시 대상과 규칙이 같은 곳에서 함께 바뀌기 때문이다 —
지표 이름을 고치면서 규칙을 빠뜨리는 사고를 구조로 막는다.

### DLQ 깊이는 알림에 쓰지 않는다

가장 알고 싶은 신호지만 CloudWatch에만 있고 Prometheus에는 없다. 대신 **DLQ로 가기
전에 먼저 움직이는 지표**를 본다.

- `adspectrum_messages_invalid_total` — 스키마 위반. 재전달 3회 뒤 DLQ로 간다
- `adspectrum_dynamodb_write_failures_total` — 쓰기 실패. 메시지가 삭제되지 않는다
- `keda_scaler_metrics_value` — 상한까지 늘어난 뒤에도 큐가 줄지 않는 상태

DLQ에 쌓인 뒤 아는 것보다 쌓이기 시작할 때 아는 편이 낫다. CloudWatch 알람으로 DLQ
자체를 거는 것은 별개의 후속 작업으로 남긴다.

### 임계값 대신 오차 예산 소진 속도

metrics-api는 "5xx가 5%를 넘으면 알린다" 대신 가용성 목표(30일 99.5%)를 정하고 그
예산을 몇 배 속도로 태우는지로 알린다.

| 알림 | 창 | 임계 | 뜻 |
|---|---|---|---|
| 빠른 소진 (critical) | 5분 · 1시간 | 14.4× | 이대로면 예산이 약 이틀에 소진 |
| 느린 소진 (warning) | 30분 · 6시간 | 6× | 당장은 아니지만 이번 주기 목표를 놓친다 |

짧은 창만 보면 1분짜리 스파이크에 사람을 깨우고, 긴 창만 보면 늦게 안다. 둘을 `and`로
묶어 둘 다 넘을 때만 울린다. 트래픽이 0이면 두 식 모두 0으로 나누어 판단하지 못하므로
`MetricsApiNoTraffic`을 따로 뒀다 — 조회가 끊긴 것도 정상은 아니다.

### 울릴 수 없는 기본 규칙을 끈다

kube-prometheus-stack은 etcd·kube-scheduler·kube-controller-manager·kube-proxy 알림을
기본으로 켠다. EKS는 컨트롤플레인을 긁을 수 없어 이 규칙들이 **영원히 발화한다.**
켜 두면 채널이 덮이고, 사람은 채널 전체를 무시하게 된다. 울릴 수 없는 알림을 끄는 것은
알림을 줄이는 일이 아니라 남은 알림을 살리는 일이다.

같은 이유로 `Watchdog`(항상 발화하는 감시용 알림)은 null 수신자로 보낸다. 이것은
알림 파이프라인이 살아 있는지 외부에서 확인하는 장치라, 채널로 보내면 소음만 된다.
실제 운영이라면 dead man's switch 서비스로 보낸다.

### 웹훅 URL은 부트스트랩에서 주입한다

Git에 넣으면 저장소를 읽을 수 있는 사람이 곧 알림 채널에 쓸 수 있다. ArgoCD 배포 키와
같은 문제라 같은 방식으로 푼다 — `install.sh`가 `monitoring` 네임스페이스와 시크릿을
먼저 만들고, Alertmanager는 그것을 파일로 마운트해 `slack_api_url_file`로 가리킨다.

**목적지가 없으면 부트스트랩을 중단한다.** 감지만 하고 아무 데도 보내지 않는 상태는
알림이 있다는 착각만 만든다. `SKIP_ALERT_WEBHOOK=1`로 넘길 수 있지만 경고를 남긴다.

### 이후 변경 (2026-08-29)

웹훅 주입 방식은 같은 날 017에서 뒤집혔다. 부트스트랩에서 사람이 넣는 대신 SSM
파라미터 스토어에 두고 External Secrets가 당겨 온다. `SKIP_ALERT_WEBHOOK`도 함께
사라졌다. 이 절의 판단(목적지 없는 알림 시스템을 허용하지 않는다)은 그대로다 —
파라미터가 비어 있으면 `ExternalSecret`이 오류로 남아 눈에 띈다.

### 검증 결과 (2026-08-29)

스키마 위반 메시지 한 건을 큐에 넣고 확인했다.

```
$ aws sqs send-message --message-body '{"broken":"schema"}'
→ ConsumerInvalidMessages  warning  active   (약 2분 뒤)
```

Alertmanager 지표로 전송까지 확인했다. `alertmanager_notifications_total{integration="slack"}`
가 6이고 `notifications_failed_total`은 모든 사유에서 0이었다. 라우팅도 의도대로 갈렸다 —
`Watchdog` 1건은 null 수신자로, 나머지 4건은 slack으로 갔다.

기본 규칙 중 `KubeCPUOvercommit`·`KubeMemoryOvercommit`도 함께 발화했다. 노드 2대에
컨슈머 10개와 발행기 3개를 얹은 상태였으니 사실이다 — 끄지 않은 기본 규칙이 실제로
쓸모 있는 신호를 준 경우다.

### 겪은 것 — 도착했는데 읽을 수 없었다

전송은 성공했지만 Slack에 찍힌 것은 이랬다.

```
{{ .CommonLabels.severity | toUpper }} · {{ .CommonLabels.alertname }}
{{ range .Alerts }}{{ .Annotations.summary }}
```

값이 아니라 템플릿 문자열 자체가 나갔다. 원인은 내가 씌운 Helm 이스케이프였다.
차트가 `alertmanager.config`를 `tpl`로 렌더링할 것이라 가정하고 `{{ "{{ ... }}" }}`로
감쌌는데, kube-prometheus-stack은 그 값을 렌더링하지 않는다. 그래서 이스케이프가 그대로
남았고, Alertmanager의 Go 템플릿이 "따옴표 안의 문자열을 출력하라"는 지시로 읽었다.

이스케이프를 걷어내고 Go 템플릿을 그대로 적어 고쳤다. 본문 줄바꿈도 `\n` 두 글자가
아니라 실제 개행이어야 해서 블록 스칼라로 바꿨다.

**전송 성공이 도착 성공은 아니다.** `notifications_total`이 늘고 `failed_total`이 0이어도
사람이 읽을 수 없는 메시지였다. 지표만 보고 "동작한다"고 적었다면 그대로 넘어갔을 것이다.
실제로 채널을 열어 본 뒤에야 알았다.

## 017. 비밀을 클러스터 밖에 두고 당겨 온다

- 날짜: 2026-08-29
- 상태: 확정 (동기화 검증은 다음 클러스터 가동 때)

### 상황

016에서 알림 웹훅을 부트스트랩 시점에 사람이 주입하게 했다. 배포 키와 같은 방식이라
일관은 있었지만, 그 방식의 한계가 그대로 따라왔다.

- 비밀이 운영자 노트북의 파일 하나에만 있다. 잃어버리면 끝이다
- 교체하려면 사람이 클러스터를 만져야 한다
- 누가 언제 읽었는지 기록이 없다
- 클러스터를 사람 없이 다시 세울 수 없다

### 두 비밀은 성격이 다르다

| 비밀 | 언제 필요한가 | 옮길 수 있나 |
|---|---|---|
| ArgoCD 배포 키 | ArgoCD가 저장소를 **읽기 전에** | 불가 — 이 키를 읽으려면 매니페스트가 필요한데 그것을 가져오는 데 이 키가 필요하다 |
| Slack 웹훅 | Alertmanager가 뜬 **뒤에** | 가능 — 클러스터가 이미 돌고 있을 때 소비된다 |

진짜 부트스트랩 비밀과 "아직 안 옮긴 비밀"의 차이다. 배포 키는 어떤 설계로도 남고,
그래서 읽기 전용·단일 저장소 한정으로 피해 범위를 줄여 뒀다. 웹훅은 남을 이유가 없다.

### 결정

웹훅을 SSM 파라미터 스토어(SecureString)에 두고 External Secrets Operator가 IRSA로
당겨 와 k8s Secret을 만든다. 부트스트랩에서 사람이 주입하는 비밀은 배포 키 하나만
남는다.

### 왜 Secrets Manager가 아니라 파라미터 스토어인가

| | 파라미터 스토어(표준) | Secrets Manager |
|---|---|---|
| 비용 | 무료 | 비밀당 월 $0.40 |
| 자동 회전 | 없음 | 있음 |
| 암호화·감사 | KMS·CloudTrail | KMS·CloudTrail |

웹훅 URL은 자동 회전 대상이 아니다. 회전이 필요한 자격증명(DB 비밀번호 등)이 생기면
그때 Secrets Manager를 쓴다. 지금 필요 없는 기능에 비용을 내지 않는다.

### 파라미터를 Terraform으로 만들지 않는다

두 가지 이유다.

**값이 state에 평문으로 남는다.** Terraform이 관리하면 SecureString이어도 state에는
값이 그대로 들어간다. 상태 파일을 읽을 수 있는 사람이 곧 비밀을 얻는다.

**`destroy`와 함께 사라진다.** 이 프로젝트는 작업하지 않는 시간에 클러스터를 내린다.
파라미터가 환경에 묶여 있으면 다시 세울 때마다 사람이 웹훅을 다시 넣어야 하고, 그러면
옮긴 의미가 없다. 상태 버킷·CI 역할과 같은 범주로 계정 사전 조건에 둔다
(DECISIONS 003, 015).

Terraform이 만드는 것은 **읽을 권한**뿐이다. `ssm:GetParameter`를 이 프로젝트의
파라미터 경로로 한정하고, SecureString 복호화를 위한 `kms:Decrypt`는
`kms:ViaService` 조건으로 SSM 경유만 허용한다.

### ServiceAccount 이름을 고정한 이유

external-secrets 차트의 기본 ServiceAccount 이름은 `<릴리스>-external-secrets`다.
릴리스 이름이 바뀌면 IRSA 신뢰 정책의 `sub` 조건과 어긋나고, 그러면 권한이 **조용히**
끊긴다. 이름을 값으로 고정했다. kube-prometheus-stack에서 Grafana ServiceAccount
이름이 릴리스 이름에서 파생되는 것과 같은 함정이다.

### 동기화 순서

`external-secrets-config`에 `sync-wave: "1"`을 달았다. ClusterSecretStore와
ExternalSecret은 차트가 설치하는 CRD가 있어야 하고, 대상 네임스페이스도 먼저 생겨야
한다. 재시도로도 회복되지만 순서가 분명한 의존은 순서로 적는 편이 읽기 쉽다.

파라미터가 비어 있으면 `ExternalSecret`이 오류 상태로 남고 Alertmanager 파드는
시크릿을 기다린다. 값을 넣는 순간 스스로 회복하므로 순서를 지킬 필요는 없다.

### 검증 결과 (2026-08-29)

클러스터를 새로 세운 뒤 사람이 아무것도 하지 않았는데 시크릿이 만들어졌다.

```
$ kubectl get externalsecret -n monitoring
NAME                 STORE     STATUS         READY   LAST SYNC
alertmanager-slack   aws-ssm   SecretSynced   True    5m59s
```

만들어진 Secret의 `webhook-url` 값은 81자로 SSM에 넣은 것과 길이가 같고, 소유자는
`ExternalSecret/alertmanager-slack`이다(`creationPolicy: Owner`). Alertmanager 파드는
그것을 마운트해 `2/2 Running`으로 떴고, 실제로 Slack에 알림을 보냈다(016 검증 결과).

부트스트랩에서 사람이 넣은 것은 배포 키 하나뿐이었다.

## 018. 파드 아래 계층도 자동으로 늘린다

- 날짜: 2026-08-29
- 상태: 확정 (동작 검증은 다음 클러스터 가동 때)

### 상황

KEDA가 큐 길이를 보고 컨슈머를 늘리지만 노드는 2대로 고정이었다. 그래서 상한을 5로
묶어 뒀는데, 그 5는 처리 능력에서 나온 값이 아니라 **노드가 감당할 수 있는 파드 수**에서
나온 값이다(DECISIONS 001). 스펙 9장이 적어 둔 원래 값은 10이었다.

스케일링이 한 계층에서 끊겨 있었다. 파드는 늘어나는데 그 파드가 앉을 자리는 늘지 않는다.

### 결정

Karpenter를 붙여 노드를 필요할 때 만들고, KEDA 상한을 스펙의 원래 값인 10으로 되돌린다.
관리형 노드그룹은 없애지 않고 고정 바닥으로 남긴다.

### 노드그룹을 없애지 않는 이유

Karpenter 자신이 어딘가에서 돌아야 한다. 자기가 만든 노드에 자기가 올라가면, 그 노드를
정리하려 할 때 스스로를 내쫓게 된다. 그래서 컨트롤러에 `karpenter.sh/nodepool`이 없는
노드에만 스케줄되도록 어피니티를 걸고, 관리형 노드그룹을 그 자리로 남겼다.

ArgoCD·Prometheus 같은 플랫폼 컴포넌트도 여기 앉는다. 이들이 Karpenter 노드에 있으면
축소될 때마다 옮겨 다니게 된다.

### Pod Identity와 IRSA가 공존한다

이 프로젝트의 파드 권한은 전부 IRSA인데, Karpenter만 Pod Identity를 쓴다. 공식 모듈
v21이 그 방식으로 바뀌었기 때문이고, 굳이 되돌리지 않았다.

| | IRSA | Pod Identity |
|---|---|---|
| 신뢰 관계 | 역할의 신뢰 정책에 OIDC subject를 적는다 | 클러스터가 연결을 관리한다 |
| 역할 지정 | ServiceAccount 어노테이션 | EKS API의 연결(association) |
| 필요한 것 | OIDC 프로바이더 | `eks-pod-identity-agent` 애드온 |

Pod Identity 쪽이 역할을 다른 클러스터에서 재사용하기 쉽고 신뢰 정책이 단순하다.
새로 만드는 것이라면 이쪽이 낫지만, 이미 IRSA로 도는 것을 옮길 이유는 없어 그대로 뒀다.
두 방식이 섞여 있다는 사실 자체는 알고 있어야 한다 — 권한이 안 붙었을 때 어디를 봐야
하는지가 달라진다.

### spot 후보를 넓힌다

인스턴스 타입을 하나로 고정하지 않고 `t/m/c` 계열의 2~4 vCPU를 모두 허용했다. spot은
특정 타입의 재고가 마르면 받지 못하는데, 후보가 넓을수록 받을 확률이 올라가고 회수도
덜 겪는다. 세대는 3세대 이상으로 잘랐다.

`limits.cpu = 16`을 둔 이유는 상한 없는 오토스케일러가 가장 비싼 실수이기 때문이다.
잘못된 파드 하나가 계정을 비울 수 있다.

### 위험을 문서가 아니라 실험으로 확인한다

SPEC 13장에 "spot 중단으로 데모 중 노드 소실"을 위험으로 적고 대응은 문장으로만 있었다.
AWS FIS 실험 템플릿을 만들어 회수를 직접 일으킨다. 확인하려는 것은 셋이다.

- Karpenter가 회수 알림(SQS)을 받아 노드를 미리 비우는가
- 컨슈머가 SIGTERM을 받고 처리 중이던 배치를 마치는가 — 유실 없이
- metrics-api의 파드 분산이 실제로 가용성을 지키는가

2분 예고를 그대로 쓴다. 더 짧게 주면 대응 과정을 관찰할 시간이 없다.

### 검증 결과 (2026-08-29)

**먼저 배운 것: 이 워크로드는 노드를 늘릴 만큼 무겁지 않다.** 부하를 초당 900건까지
올려 컨슈머가 상한 10까지 늘어났지만 파드는 하나도 Pending이 되지 않았다. 요청이
50m이라 10개가 기존 노드 2대에 다 들어간다. KEDA 상한을 5로 묶었던 옛 제약은 파드
수용량이었고(DECISIONS 001), prefix delegation으로 그것이 풀린 뒤로는 CPU도 여유가 있다.

그래서 Karpenter는 표준 방식으로 확인했다 — 들어갈 수 없는 파드를 만들어 본다.

| 확인 | 결과 |
|---|---|
| 노드 생성 | 1 vCPU 파드 3개 배포 → **33초 만에** `c5a.xlarge` spot 노드 생성, 전부 Running |
| 인스턴스 선택 | 후보(t/m/c · 2~4 vCPU) 중에서 골랐다. 회수 뒤 교체분은 `t3.xlarge`였다 |
| 축소 | 파드 제거 후 3분 40초 뒤 `"reason":"underutilized","decision":"delete"`로 노드 삭제 |

**spot 회수 실험.** FIS로 회수를 일으키고 1분 안에 복구되는 것을 봤다.

```
23:04:32  실험 시작
23:05:05  노드에 karpenter.sh/disrupted 테인트, 파드 3개 전부 축출
23:05:38  새 노드에서 3개 전부 Running
```

Karpenter 로그가 경로를 그대로 보여 준다.

```
"initiating delete from interruption message"
  queue: "adspectrum-eks-karpenter"  messageKind: "spot_interrupted"
  action: "CordonAndDrain"
```

이전 인스턴스(`i-0627…`)는 `terminated`, 새 인스턴스는 `i-03e2…`로 바뀌었다. 그동안
파이프라인의 DLQ는 1건이었는데 그것은 알림 시험용으로 직접 넣은 스키마 위반 메시지이고,
회수로 생긴 유실은 없었다.

### 겪은 것 — 관리형 정책 크기 상한

첫 apply에서 컨트롤러 IAM 정책 생성이 실패했다.

```
Error: creating IAM Policy: LimitExceeded: Cannot exceed quota for PolicySize: 6144
```

Karpenter가 요구하는 권한 집합이 관리형 정책의 6,144자를 넘는다. 모듈이 이 상황을
예상하고 `enable_inline_policy` 옵션을 두었고(설명에 같은 오류 문구가 적혀 있다),
인라인 역할 정책의 상한은 10,240자다. 그 옵션을 켜서 해결했다.

부트스트랩 초기에 Karpenter가 `"failed listing instance types: no subnets found"`를
몇 번 남기는데, EC2NodeClass가 아직 동기화되기 전이라 그렇다. 뒤 물결에서 CR이
적용되면 사라진다.

## 019. 이미지 취약점은 올라가기 전에 막는다

- 날짜: 2026-08-30
- 상태: 확정

### 상황

ECR 리포지토리에 `scan_on_push = true`를 켜 두었지만 **아무도 그 결과를 보지 않았다.**
스캔은 돌고 있는데 무엇도 막지 않는 상태였다. 켜 두었다는 사실만으로 안심하게 되는
쪽이 켜지 않은 것보다 나쁠 수도 있다.

### 결정

CI에 `trivy image`를 넣고, 고칠 수 있는 HIGH·CRITICAL이 있으면 **푸시 전에** 실패시킨다.
SBOM(CycloneDX)을 함께 만들어 워크플로 산출물로 보관한다.

### 왜 푸시 전인가

ECR 태그가 불변이라 한번 올라간 이미지는 지우지 않는 한 그 자리에 남고, 지우는 것은
되돌릴 수 없다(DECISIONS 012에서 실제로 겪었다). 올린 뒤 검사해서 "문제가 있다"고
알리면 이미 늦다. 검사를 통과한 것만 레지스트리에 들어가게 한다.

같은 이유로 PR에서도 돈다. 이 잡은 AWS를 건드리지 않아 자격증명 없이 실행되므로,
머지 전에 알 수 있다.

### `--ignore-unfixed`를 쓰는 이유

수정본이 없는 취약점까지 실패로 처리하면 파이프라인이 상시 빨간불이 된다. 베이스
이미지에 항상 몇 건은 있고, 우리가 할 수 있는 일이 없다. 사람은 늘 빨간 신호를
무시하게 되고, 그러면 **고칠 수 있는 것이 새로 생겨도 묻힌다.**

`.trivyignore.yaml`에 이유를 적어 예외를 관리한 것과 같은 판단이다(DECISIONS 015).
막을 수 없는 것으로 막으면 막아야 할 것을 놓친다.

### SBOM을 남기는 이유

새 취약점이 공개됐을 때 가장 먼저 답해야 하는 질문은 "우리가 그것을 쓰고 있었나"다.
SBOM이 없으면 이미지를 다시 뜯어야 하고, 그 이미지가 이미 지워졌다면 답할 방법이 없다.
CycloneDX 형식으로 만들어 30일 보관한다 — 이 프로젝트의 배포 주기에는 그 정도면 충분하고,
길게 두려면 아티팩트 대신 S3나 ECR 어테스테이션으로 옮기는 것이 맞다.

### 빌드를 두 번 하지 않는다

검사하려면 이미지가 먼저 있어야 하는데, 푸시 잡에서 다시 구우면 같은 것을 두 번
만든다. 검사 잡에서 `--cache-to type=gha`로 캐시를 남기고 푸시 잡이 `--cache-from`으로
받아 간다.

푸시 명령에 `--provenance=false`를 함께 붙였다. RUNBOOK의 로컬 절차와 CI가 같은
명령을 쓰게 하려는 것이고, attestation이 불변 태그를 차지하는 사고(DECISIONS 012)를
CI에서도 원천 차단한다.
