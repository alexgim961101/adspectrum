## 001. 노드 파드 수용량 부족 — VPC CNI prefix delegation

- 날짜: 2026-08-22
- 상태: 결정 (SPEC 6장·9장 반영)

### 상황

VPC CNI 기본 모드에서 노드가 띄울 수 있는 파드 수는 인스턴스 타입이 정한다.
공식은 `ENI 수 × (ENI당 IP - 1) + 2`이고, t3.medium은 ENI 3개 / ENI당 IP 6개라 **17개**가 상한이다.
노드 2대면 클러스터 전체가 34개다.

계획된 상주 컴포넌트를 세면 kube-system 6, ArgoCD 7, kube-prometheus-stack 7,
KEDA·Argo Rollouts·ALB Controller 6, 애플리케이션 3 — 약 **29개**다.
여유가 5개뿐인데 KEDA는 consumer를 최대 10개까지 늘리도록 계획되어 있었다.

즉 부하를 주면 consumer 파드 절반이 `Pending`으로 남는다. 이 프로젝트는 클러스터 오토스케일러와
Karpenter를 범위에서 제외했으므로 **노드가 스스로 늘지도 않는다**. 노드그룹의 `max 4`는
아무도 조정하지 않으면 의미가 없다. 완료 조건 3번(consumer 0→N→0 스케일 그래프)이 성립하지 않는다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | VPC CNI prefix delegation 활성화 | ENI에 개별 IP 대신 `/28` 접두사를 할당해 t3.medium도 파드 110개까지 수용. 애드온 설정 변경뿐 |
| B | 노드를 t3.large로 교체 | 메모리가 4GB→8GB로 늘지만 IP 상한(35개)은 여전히 낮고 비용이 오른다 |
| C | KEDA 상한을 낮춘다 | 코드 변경은 가장 작지만 데모 곡선의 설득력이 줄어든다 |
| D | 클러스터 오토스케일러 도입 | 근본 해결이지만 SPEC 12장에서 범위 제외한 항목이고 1주 일정에 맞지 않는다 |

### 결정

**A + C를 함께 적용한다.** vpc-cni 애드온에 prefix delegation을 켜고, KEDA `maxReplicaCount`는 5로 둔다.

### 근거

A를 택한 이유는 인스턴스 타입을 바꾸지 않고 IP 병목만 제거할 수 있기 때문이다.
프라이빗 서브넷을 `/20`(4,091개)으로 넓게 잡아 둔 설계가 여기서 쓰인다 — prefix delegation은
서브넷에서 `/28` 블록 단위로 주소를 떼어가므로 좁은 서브넷에서는 오히려 할당 실패가 난다.

C를 함께 적용한 이유는 A만으로는 병목이 IP에서 **메모리**로 옮겨갈 뿐이기 때문이다.
t3.medium 2대의 실제 할당 가능 메모리는 8GB에 못 미치고, Prometheus와 ArgoCD가 그중 상당량을 쓴다.
consumer는 SQS를 폴링해 DynamoDB에 집계를 반영하는 가벼운 워커라 5개로도
큐 길이에 반응하는 0→N→0 곡선은 충분히 관측된다. 상한을 10으로 두고 파드가 `Pending`에 걸리는 것보다,
5로 두고 전부 정상 기동하는 편이 데모로서 정확하다.

B는 메모리 부족이 실제로 관측된 뒤에 쓴다. 지금 인스턴스를 키우면 원인 확인 없이 비용부터 늘리는 셈이다.

### 남는 위험

prefix delegation은 노드가 실제로 파드를 110개까지 띄울 수 있다는 뜻이 아니다. IP 제약이 사라진 뒤의
한계는 CPU와 메모리이므로, 2일차에 플랫폼 컴포넌트를 올린 직후 `kubectl top nodes`로 여유를 확인하고
부족하면 B로 전환한다.
