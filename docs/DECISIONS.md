## 001. 노드 파드 수용량 부족 — VPC CNI prefix delegation

- 날짜: 2026-08-22
- 상태: 결정 (SPEC 6장·9장 반영)

### 상황

VPC CNI 기본 모드에서 노드가 띄울 수 있는 파드 수는 인스턴스 타입이 정한다.
공식은 `ENI 수 × (ENI당 IP - 1) + 2`이고, t3.medium은 ENI 3개 / ENI당 IP 6개라 **17개**가 상한이다.
노드 2대면 클러스터 전체가 34개다.

계획된 상주 컴포넌트를 세면 kube-system 6, ArgoCD 7, kube-prometheus-stack 7,
KEDA·Argo Rollouts·ALB Controller 6, 애플리케이션 3 — 약 **29개**다.
여유가 5개뿐인데 KEDA는 consumer를 최대 10개까지 늘리도록 계획되어 있었다.

즉 부하를 주면 consumer 파드 절반이 `Pending`으로 남는다. 이 프로젝트는 클러스터 오토스케일러와
Karpenter를 범위에서 제외했으므로 **노드가 스스로 늘지도 않는다**. 노드그룹의 `max 4`는
아무도 조정하지 않으면 의미가 없다. 완료 조건 3번(consumer 0→N→0 스케일 그래프)이 성립하지 않는다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | VPC CNI prefix delegation 활성화 | ENI에 개별 IP 대신 `/28` 접두사를 할당해 t3.medium도 파드 110개까지 수용. 애드온 설정 변경뿐 |
| B | 노드를 t3.large로 교체 | 메모리가 4GB→8GB로 늘지만 IP 상한(35개)은 여전히 낮고 비용이 오른다 |
| C | KEDA 상한을 낮춘다 | 코드 변경은 가장 작지만 데모 곡선의 설득력이 줄어든다 |
| D | 클러스터 오토스케일러 도입 | 근본 해결이지만 SPEC 12장에서 범위 제외한 항목이고 1주 일정에 맞지 않는다 |

### 결정

**A + C를 함께 적용한다.** vpc-cni 애드온에 prefix delegation을 켜고, KEDA `maxReplicaCount`는 5로 둔다.

### 근거

A를 택한 이유는 인스턴스 타입을 바꾸지 않고 IP 병목만 제거할 수 있기 때문이다.
프라이빗 서브넷을 `/20`(4,091개)으로 넓게 잡아 둔 설계가 여기서 쓰인다 — prefix delegation은
서브넷에서 `/28` 블록 단위로 주소를 떼어가므로 좁은 서브넷에서는 오히려 할당 실패가 난다.

C를 함께 적용한 이유는 A만으로는 병목이 IP에서 **메모리**로 옮겨갈 뿐이기 때문이다.
t3.medium 2대의 실제 할당 가능 메모리는 8GB에 못 미치고, Prometheus와 ArgoCD가 그중 상당량을 쓴다.
consumer는 SQS를 폴링해 DynamoDB에 집계를 반영하는 가벼운 워커라 5개로도
큐 길이에 반응하는 0→N→0 곡선은 충분히 관측된다. 상한을 10으로 두고 파드가 `Pending`에 걸리는 것보다,
5로 두고 전부 정상 기동하는 편이 데모로서 정확하다.

B는 메모리 부족이 실제로 관측된 뒤에 쓴다. 지금 인스턴스를 키우면 원인 확인 없이 비용부터 늘리는 셈이다.

### 검증 결과 (2026-08-23)

첫 `apply` 후 두 노드 모두 `allocatable.pods = 110`으로 확인됐다. `aws-node`에 `ENABLE_PREFIX_DELEGATION=true`,
`WARM_PREFIX_TARGET=1`이 적용된 것도 확인했다. 애드온을 노드그룹보다 먼저 적용한 순서가 의도대로 동작했다.

### 남는 위험

IP 제약은 사라졌지만 한계가 메모리로 옮겨갔다. 측정된 할당 가능 메모리는 노드당 약 3.2GiB,
2대 합계 약 6.4GiB다. 여기에 ArgoCD, kube-prometheus-stack, KEDA, Argo Rollouts, ALB Controller가
올라가면 여유가 크지 않다. 2일차에 플랫폼 컴포넌트를 올린 직후 파드가 `Pending`에 걸리는지 확인하고,
메모리 부족이 원인이면 그때 B(t3.large)로 전환한다. 지금 미리 인스턴스를 키우지는 않는다.

## 002. EKS 엔드포인트 공개와 컨트롤플레인 로그 비활성화

- 날짜: 2026-08-22
- 상태: 결정

### 상황

EKS 모듈의 기본값 두 가지가 이 프로젝트의 제약과 맞지 않았다.
퍼블릭 엔드포인트는 기본이 **비활성**이라 그대로 두면 로컬에서 `kubectl`과 `helm`을 쓸 수 없고,
컨트롤플레인 로그는 기본이 **활성**(`audit`, `api`, `authenticator`)이라 CloudWatch 수집량만큼 과금된다.

### 결정

퍼블릭 엔드포인트는 열고 소스 IP 제한은 걸지 않는다. 프라이빗 엔드포인트도 함께 켠다.
컨트롤플레인 로그는 전부 끄고 로그 그룹도 만들지 않는다.

### 근거

엔드포인트를 연 이유는 부트스트랩 경로가 로컬 노트북 하나뿐이기 때문이다. 프라이빗 전용으로 두면
배스천이나 VPN이 필요한데, 그 자체가 이 프로젝트에서 증명하려는 대상이 아니면서 비용과 일정을 잡아먹는다.
API 엔드포인트는 IAM으로 인증되므로 열려 있다는 것이 곧 접근 가능하다는 뜻은 아니다.
소스 IP를 제한하지 않은 것은 작업 위치가 바뀔 때마다 `apply`를 다시 해야 하는 마찰 때문이고,
실서비스라면 제한하거나 프라이빗 전용 + 배스천으로 가는 것이 맞다.
프라이빗 엔드포인트를 함께 켠 이유는 노드가 VPC 내부 경로로 컨트롤플레인에 붙어 NAT 트래픽을 줄이기 때문이다.

로그를 끈 이유는 audit 로그의 양이 많고 ArgoCD처럼 API 서버를 지속적으로 폴링하는 컴포넌트가
있으면 더 늘기 때문이다. 이 프로젝트의 관측 책임은 Prometheus와 Grafana에 있고 완료 조건 어디에도
컨트롤플레인 로그가 들어가지 않는다. 보안 감사가 요구되는 환경이라면 최소한 `audit`은 켜야 한다.

### 남는 위험

컨트롤플레인 로그가 없으므로 API 서버 수준의 문제(권한 거부 원인, 웹훅 실패 등)를 사후에 추적할 수 없다.
그런 문제를 만나면 일시적으로 `audit`만 켜서 재현하고 다시 끈다.

## 003. GitHub Actions OIDC 프로바이더를 만들지 않고 참조한다

- 날짜: 2026-08-22
- 상태: 결정

### 상황

CI가 장기 액세스 키 없이 ECR에 푸시하려면 계정에 GitHub Actions OIDC 프로바이더가 있어야 한다.
그런데 이 프로바이더는 **계정당 하나만 존재할 수 있는 공용 리소스**이고, 대상 계정에는 이미
다른 프로젝트가 만들어 둔 것이 있었다. Terraform이 새로 만들려 하면 apply가 중복으로 실패한다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 데이터 소스로 기존 것을 참조 | 소유하지 않으므로 destroy가 다른 프로젝트에 영향을 주지 않는다 |
| B | `terraform import`로 소유권을 가져온다 | destroy할 때 계정의 다른 CI가 전부 끊긴다 |
| C | 조건부 생성 플래그를 둔다 | 계정 상태에 따라 동작이 갈리는 설정이 하나 늘어난다 |

### 결정

**A.** `aws_iam_openid_connect_provider` 데이터 소스로 참조만 한다.

### 근거

이 프로젝트는 비용 때문에 매일 `terraform destroy`를 실행한다. B를 택하면 그때마다 같은 계정의
다른 프로젝트 CI 인증이 함께 끊긴다. 리소스의 수명이 프로젝트보다 길고 소유자가 따로 있다면
IaC에서도 만들지 않고 참조하는 것이 맞다.

대가는 이 코드가 자기완결적이지 않다는 점이다. 프로바이더가 없는 새 계정에서는 `apply`가 실패하므로,
사전 조건임을 RUNBOOK에 적고 필요한 생성 명령을 함께 남긴다.

### 검증 결과 (2026-08-23)

첫 `destroy` 후 GitHub Actions OIDC 공급자가 계정에 그대로 남은 것을 확인했다.
반면 이 프로젝트가 소유한 EKS 클러스터용 OIDC 공급자는 함께 삭제됐다.
소유와 참조를 나눈 판단이 의도대로 동작했고, B(import)를 택했다면 이 시점에 계정의
다른 프로젝트 CI 인증이 끊겼을 것이다.

## 004. 스펙에 없던 ALB Controller IRSA 역할 추가

- 날짜: 2026-08-23
- 상태: 결정 (SPEC 6장 보완)

### 상황

2일차 컴포넌트를 구성하다 스펙 6장의 IRSA 매핑 표에 **AWS Load Balancer Controller가
빠져 있는 것**을 발견했다. 이 컨트롤러는 Ingress를 보고 실제 ALB와 리스너, 대상 그룹,
보안 그룹 규칙을 만들기 때문에 상당한 AWS 권한이 필요하다. 권한이 없으면 Ingress가
생성되지 않고, 2일차 완료 기준인 "전 앱 Synced/Healthy"를 채울 수 없다.
3일차 API 노출과 6일차 카나리 트래픽 분할도 전부 여기에 걸린다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 벤더가 발행한 공식 정책을 그대로 가져와 쓴다 | 검증된 권한 집합. 다만 쓰지 않는 권한도 포함된다 |
| B | 실제로 필요한 동작만 추려 직접 작성한다 | 최소 권한에 가깝지만 누락 시 Ingress가 조용히 실패한다 |
| C | 커뮤니티 IAM 모듈의 내장 정책을 쓴다 | 코드는 짧지만 이 프로젝트에 IAM 관리 방식이 두 가지가 된다 |

### 결정

**A.** 공식 정책 JSON을 `infra/modules/iam/policies/`에 버전과 출처를 명시해 보관하고
`file()`로 읽어 인라인 정책으로 붙인다.

### 근거

이 프로젝트의 다른 IRSA 정책은 전부 파드가 실제로 호출하는 API만 나열한 최소 권한이다.
Load Balancer Controller만 예외로 둔 이유는 필요한 동작이 80개가 넘고 컨트롤러 버전마다
바뀌기 때문이다. B를 택하면 누락된 권한 하나 때문에 Ingress 생성이 실패하는데, 원인이
컨트롤러 로그에만 남아 찾는 데 시간이 든다. 7일 일정에서 감수할 위험이 아니다.

대신 무엇을 주는지 모르고 쓰지는 않는다. `policies/README.md`에 서비스별 동작 수와
이 프로젝트에서 쓰지 않는 권한(WAF, Shield, ACM, Cognito)을 정리했다.
"최소 권한"과 "벤더 정책 신뢰"의 경계를 어디에 두었는지가 기록으로 남아야 한다.

C를 택하지 않은 이유는 IAM 역할 5개는 직접 작성하고 하나만 모듈로 만드는 구성이
읽는 사람에게 일관성 없게 보이기 때문이다.

### 남는 위험

정책에 이 프로젝트가 쓰지 않는 WAF·Shield·ACM·Cognito 권한이 포함된다. 잘라낼 수는 있지만
다음 컨트롤러 버전에서 조용히 깨질 수 있어 그대로 둔다. 실제 운영이라면 컨트롤러 버전을
올릴 때 정책 diff를 확인하는 절차를 두어야 한다.

## 005. 매니페스트에 AWS 계정 ID를 그대로 적는다

- 날짜: 2026-08-23
- 상태: 결정

### 상황

IRSA는 ServiceAccount 어노테이션에 역할 ARN 전체를 요구하고, ARN에는 계정 ID가 들어간다.
이 저장소는 채용 담당자가 열람하는 포트폴리오라 계정 ID가 공개될 수 있다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 매니페스트에 ARN을 그대로 적는다 | Git에 있는 것이 곧 클러스터 상태라는 GitOps 전제가 유지된다 |
| B | 부트스트랩 시점에 치환한다 | 계정 ID는 감춰지지만 Git만으로는 배포가 재현되지 않는다 |
| C | 저장소를 비공개로 둔다 | 포트폴리오로서의 목적과 충돌한다 |

### 결정

**A.** ARN을 매니페스트에 그대로 적는다.

### 근거

B는 GitOps의 핵심 전제를 깬다. Git을 봐도 실제로 무엇이 배포되는지 알 수 없게 되고,
"Git이 유일한 진실"이라는 주장이 성립하지 않는다. 이 프로젝트가 증명하려는 것이 바로
그 전제이므로, 그것을 훼손하면서 얻는 이득이 없다.

계정 ID는 자격증명이 아니다. AWS도 비밀로 분류하지 않으며, 이것만으로는 어떤 접근도
불가능하다. 실제 방어선은 IAM 정책과 신뢰 정책 조건이고, 그쪽은 네임스페이스와
ServiceAccount 이름까지 좁혀 두었다.

### 남는 위험

계정 ID가 알려지면 역할 이름 추측을 통한 열거 시도의 출발점이 될 수 있다. 다만 신뢰 정책이
이 클러스터의 특정 ServiceAccount로 제한되어 있어 외부에서 역할을 맡을 수 없다.
민감도가 높은 조직이라면 저장소를 비공개로 두거나 배포 계정을 분리하는 것이 맞다.

## 006. ALB Controller가 IMDS에 접근하지 못해 기동 실패

- 날짜: 2026-08-23
- 상태: 해결

### 증상

2일차 부트스트랩 후 `aws-load-balancer-controller` 파드가 `CrashLoopBackOff`에 빠졌다.
IRSA 어노테이션은 정상이었고 역할도 붙어 있었는데 로그는 이렇게 나왔다.

```
unable to initialize AWS cloud
error: failed to get VPC ID: failed to fetch VPC ID from instance metadata:
       get mac metadata: operation error ec2imds: GetMetadata, canceled, context deadline exceeded
```

권한 문제가 아니라 **컨트롤러가 자기가 속한 VPC를 찾지 못하는** 문제였다.

### 원인

컨트롤러는 VPC ID와 리전을 EC2 인스턴스 메타데이터(IMDS)에서 읽는다. 그런데 노드 시작
템플릿의 `HttpPutResponseHopLimit`이 **1**이었다. 파드는 CNI를 거쳐 한 홉 떨어져 있으므로
홉 제한이 1이면 IMDS에 도달할 수 없다. 이건 결함이 아니라 보안 기본값이다 — 파드가 IMDS에
닿으면 **노드의 IAM 역할 자격증명을 훔칠 수 있어** IRSA로 권한을 나눈 의미가 사라진다.

### 연쇄 피해

컨트롤러가 죽어 있는 동안 그것이 등록한 mutating webhook(`mservice.elbv2.k8s.aws`)은 살아 있었다.
웹훅에 엔드포인트가 없으니 **클러스터 전체에서 Service 생성이 실패**했고, KEDA와
kube-prometheus-stack의 동기화가 함께 무너졌다. 표면적으로는 세 앱이 각각 고장 난 것처럼 보였지만
원인은 하나였다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | `vpcTags`로 VPC를 태그 조회하게 한다 | IMDS 불필요. VPC ID가 바뀌어도 매니페스트가 그대로다 |
| B | 노드의 IMDS 홉 제한을 2로 올린다 | 동작하지만 모든 파드가 노드 자격증명에 접근할 수 있게 된다 |
| C | `vpcId`를 매니페스트에 직접 적는다 | destroy/apply마다 VPC ID가 바뀌어 매일 고쳐야 한다 |

### 결정

**A.** `region`을 명시하고 VPC는 `vpcTags`(`Project=adspectrum`, `Environment=dev`)로 찾게 했다.

### 근거

B는 이 프로젝트가 IRSA로 파드별 권한을 나눈 것과 정면으로 충돌한다. 홉 제한 1은 그 설계를
강제하는 장치이므로, 컨트롤러 하나를 위해 클러스터 전체의 방어선을 낮출 이유가 없다.

C는 매일 인프라를 내렸다 올리는 이 프로젝트의 운영 방식과 맞지 않는다. Git에 적힌 값이 하루 만에
낡는다면 "Git이 유일한 진실"이라는 전제가 성립하지 않는다.

A는 태그가 provider `default_tags`로 항상 붙기 때문에 VPC를 몇 번을 다시 만들어도 유효하다.
필요한 `ec2:DescribeVpcs` 권한은 벤더 정책에 이미 포함되어 있었다.

### 함께 고친 것

동기화가 한 번 실패한 뒤 `OutOfSync`에서 멈춰 사람이 개입해야 했다. 자식 Application에
재시도 정책(`limit 5`, 15초부터 지수 백오프)을 추가해 일시적 실패에서 스스로 회복하게 했다.
웹훅이나 CRD 준비 순서 때문에 첫 시도가 실패하는 것은 흔한 일이라, 재시도가 없으면
클러스터를 다시 만들 때마다 같은 개입이 필요하다.

### 배운 것

어드미션 웹훅을 등록하는 컨트롤러가 죽으면 그 여파가 컨트롤러 자신에 그치지 않는다.
증상이 여러 곳에서 동시에 나타날 때 각각을 따로 고치려 들면 시간을 잃는다.
이번에는 세 앱이 고장 난 것처럼 보였지만 실제 원인은 하나였고, 그것을 고치자 나머지는 저절로 풀렸다.

## 007. 앱 3종을 독립 패키지로 유지한다

- 날짜: 2026-08-25
- 상태: 확정

### 상황

3일차에 앱 3종을 구현하면서 겹치는 코드가 생겼다. JSON 로깅 설정(약 40줄), 환경변수
로딩, 이벤트 스키마 상수가 generator와 consumer 양쪽에 필요하다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 앱마다 독립 패키지. 겹치는 코드는 복사 | 빌드 컨텍스트가 `apps/<앱>/` 하나. 배포 단위가 서로 독립 |
| B | uv workspace + `libs/common` 공통 패키지 | 중복 제거. 빌드 컨텍스트가 레포 루트가 되고 CI 필터가 복잡해짐 |

### 결정

**A.** 앱마다 `pyproject.toml`, `uv.lock`, `Dockerfile`을 따로 둔다.

### 근거

겹치는 코드가 앱당 40줄 남짓인 데 비해 B의 대가가 크다. `libs/**`가 바뀌면 CI의
`paths` 필터가 세 앱을 전부 다시 빌드해야 하고, Dockerfile마다 레포 루트를 컨텍스트로
잡아 필요 없는 파일까지 끌어들인다. 앱이 5개를 넘거나 공통 코드가 수백 줄이 되면
그때 B로 옮기는 편이 낫다.

이벤트 스키마가 generator와 consumer에 각각 있는 것은 중복이 아니라 **경계**다. 둘 사이의
계약은 파이썬 타입이 아니라 SQS에 실린 JSON이고, 그 계약은 `docs/API.md`에 적는다.
한쪽을 고치면 다른 쪽이 자동으로 따라오는 구조였다면, 실제로는 호환성 없는 변경을
배포한 뒤에야 알아차렸을 것이다.

## 008. 맥(arm64)에서 노드(amd64)용 이미지를 빌드한다

- 날짜: 2026-08-25
- 상태: 확정

### 상황

개발 환경은 Apple Silicon(arm64)이고, 노드는 `t3.medium`(amd64)이다. 기본값으로
빌드한 이미지를 노드에 올리면 파드가 `exec format error`로 죽는다.

### 결정

빌드할 때 `--platform linux/amd64`를 명시한다. 4일차 CI에서도 같은 값을 쓴다.

### 근거

멀티 아키텍처 이미지(`--platform linux/amd64,linux/arm64`)를 만드는 방법도 있지만
빌드 시간이 두 배가 되고, 노드가 전부 amd64인 이 프로젝트에서는 쓰지 않는 절반을
만드는 셈이다. Graviton 노드를 섞는다면 그때 필요해진다.

이 결정은 로컬에서만 문제가 되고 CI(x86 러너)에서는 드러나지 않는다. 그래서 명령을
`docs/RUNBOOK.md`에 남긴다 — 로컬에서 급히 이미지를 굽는 상황에서 잊기 쉽다.

## 009. 스키마 위반 메시지 하나가 컨슈머를 영구히 멈출 뻔했다

- 날짜: 2026-08-25
- 상태: 해결

### 증상

`aggregate()`의 테스트를 쓰는 중, 오프셋 없는 `occurred_at`("2026-08-25T09:30:12")을
넣은 케이스에서 예외가 함수 밖으로 튀어나왔다.

### 원인

깨진 메시지를 걸러 내는 `try` 블록이 `parse_event()`만 감싸고 있었고, 분 버킷을 계산하는
`minute_bucket()`은 블록 밖에 있었다. `minute_bucket()`이 던지는 `ValueError`는 잡히지 않는다.

문제는 여기서 끝나지 않는다. 이 설계에서 **처리 실패한 메시지는 삭제하지 않는다**.
따라서 예외로 폴링이 죽으면 그 메시지는 큐에 남고, 재시작한 컨슈머가 같은 메시지를 다시 받아
같은 자리에서 또 죽는다. 메시지 하나가 파이프라인 전체를 무한히 멈추는 poison pill이 된다.

### 결정

버킷 키 계산을 `try` 블록 안으로 옮겼다. 위반 메시지는 집계에서 빠지고 `ReceiptHandle`도
삭제 목록에 들어가지 않으므로, SQS가 3회 재전달한 뒤 DLQ로 옮긴다.

### 배운 것

"실패한 메시지를 삭제하지 않는다"는 안전한 규칙이지만, 그 앞단에서 **어떤 실패를 걸러 낼지**
범위를 잘못 잡으면 같은 규칙이 정확히 반대로 작동한다. 재전달이 복구 수단이 되려면
재전달된 메시지가 다음 번에는 다르게 처리되어야 하는데, 여기서는 그렇지 않았다.

DLQ를 만들어 둔 것이 이 설계의 전제였고, 그 전제가 코드에서 성립하는지는 테스트가 확인했다.

## 010. GitHub OIDC가 immutable subject로 바뀌어 CI 인증이 실패

- 날짜: 2026-08-25
- 상태: 해결

### 증상

4일차 CI의 첫 실행에서 변경 감지와 테스트는 통과했는데 ECR 푸시 단계가 죽었다.

```
Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity
```

역할의 신뢰 정책, OIDC 공급자의 대상(audience), 워크플로의 `id-token: write` 권한을
차례로 확인했지만 전부 정상이었다. 공급자도 `sts.amazonaws.com`을 허용하고 있었다.

### 원인

추측을 멈추고 토큰의 실제 클레임을 찍었다. 일회성 워크플로에서 OIDC 토큰을 발급받아
페이로드만 디코드했다(토큰 자체는 출력하지 않는다).

```json
{
  "sub": "repo:alexgim961101@74600075/adspectrum@1343590586:ref:refs/heads/main",
  "aud": "sts.amazonaws.com",
  "repository": "alexgim961101/adspectrum"
}
```

GitHub이 **immutable subject claim**으로 전환해 `sub`에 소유자와 저장소의 숫자 ID를
함께 싣고 있었다. 1일차에 작성한 신뢰 정책은 이름만 담은 예전 형식
`repo:alexgim961101/adspectrum:ref:refs/heads/main`을 `StringEquals`로 고정하고 있어
문자열이 달라 매칭에 실패한 것이다.

`gh api repos/<owner>/<repo>/actions/oidc/customization/sub`가 `use_immutable_subject: false`를
반환하는데도 실제 토큰은 ID가 박힌 형식이었다. 설정 값만 믿었다면 원인을 못 찾았을 것이다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 신뢰 정책을 ID가 박힌 새 형식으로 교체 | 토큰과 일치. ID는 불변이라 이름 변경에도 안전 |
| B | 두 형식을 모두 허용 (`StringEquals`에 값 두 개) | 롤백 대비는 되지만 예전 형식의 취약점이 남는다 |
| C | `sub`를 `StringLike`로 느슨하게 | 조건이 넓어져 고정 효과가 줄어든다 |

### 결정

**A.** `repo:<owner>@<owner_id>/<repo>@<repo_id>:ref:refs/heads/<branch>` 형식으로 바꿨다.
숫자 ID는 `locals.tf`에 두고, 확인 명령을 주석으로 남겼다.

### 근거

B는 예전 형식을 남겨 두는 것이고, 그 형식이 폐기되는 이유 자체가 보안 문제다. 저장소 이름은
바꿀 수 있고 반납한 이름은 다른 사람이 가져갈 수 있다. 이름으로만 신뢰를 고정하면 그 경로로
남의 저장소 워크플로가 우리 역할을 맡을 수 있다. GitHub이 ID를 넣기 시작한 게 정확히 그 구멍을
막으려는 것이므로, 굳이 열어 둘 이유가 없다.

숫자 ID가 매니페스트에 드러나는 가독성 손해는 있지만, 계정 ID를 그대로 적기로 한 결정
(DECISIONS 005)과 같은 성격이다 — Git에 적힌 값이 곧 배포되는 값이어야 한다.

### 배운 것

인증 실패를 디버깅할 때 **설정을 세 번 읽는 것보다 토큰을 한 번 열어 보는 것이 빠르다.**
이번에는 양쪽 설정이 모두 "맞게" 보였고, 틀린 것은 그 사이에 오가는 값이었다.
GitHub API가 보고하는 설정과 실제 발급 토큰이 달랐다는 점도 같은 교훈이다.
